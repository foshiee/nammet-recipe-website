# CLAUDE.md

Static recipe website: vanilla HTML/CSS/JS served by nginx, with recipes stored as plain JSON files. The front end has no build step and no dependencies. A small optional Node service (`opt/nomnoms-api`) adds login, recipe import and an admin page. The site browses and cooks without it.

## Layout

The repo mirrors the target server's filesystem, so paths map 1:1 onto the recipe VM:

| Repo path | Deployed to | Purpose |
|---|---|---|
| `var/www/nomnoms/index.html` | `/var/www/nomnoms/` | Shell page: a `<main id="app">` plus `app.js` (deferred). |
| `var/www/nomnoms/app.js` | same | The entire front end (one IIFE), including the sign-in, import and admin screens. |
| `var/www/nomnoms/style.css` | same | All styling; light/dark via `prefers-color-scheme` and CSS variables in `:root` (the defaults; `theme/theme.css` overrides them). |
| `var/www/nomnoms/theme/` | same | **Generated, gitignored.** `theme.css`, `site.json` and the favicon, written by the service from the admin page's settings. Absent on a site without the service, which then uses the defaults. |
| `var/www/nomnoms/recipes/*.json` | same | Recipe data served to the browser. Only `example-recipe.json` is tracked. |
| `var/www/nomnoms/photos/` | same | Recipe photos named by a recipe's `image` field. The service writes `<slug>-<hash>.jpg` files here; hand-placed files are allowed too. Only the example recipe's photo (a drawn placeholder) is tracked. |
| `var/www/nomnoms/robots.txt` | same | Turns away AI crawlers and keeps search engines out of `/recipes/`, `/photos/` and `/api/`. Its AI list matches the user-agent block in the nginx config; keep them in sync. |
| `opt/nomnoms-api/` | `/opt/nomnoms-api/` | Node service for login, import and admin, proxied at `/api/`. See below. |
| `etc/nginx/conf.d/nginx-nomnoms.conf` | `/etc/nginx/conf.d/nomnoms.conf` | Server block (note the rename on deploy). |
| `etc/nginx/nginx.conf` | `/etc/nginx/nginx.conf` | Stock RHEL-style main config; includes `conf.d/*.conf`. |
| `etc/systemd/system/nomnoms-api.service` | same | systemd unit for the service, which can write only to the recipes and photos folders, `theme/` and `/var/lib/nomnoms`. |
| `etc/nomnoms/api.env.example` | `/etc/nomnoms/api.env` | Service settings, including `ANTHROPIC_API_KEY` (an admin-page key overrides it). The real file is never committed. |
| `docs/recipe-format.md` | n/a | Authoritative recipe JSON spec. |
| `docs/install.md` | n/a | Server setup from a fresh Rocky Linux 10 VM, running the import service, and the security checklist. |
| `docs/example-recipe.json` | n/a | Example using every field. Duplicate of the copy under `var/www/nomnoms/recipes/`; keep both in sync. |
| `recipes/` (repo root) | n/a | **Gitignored** (`/recipes` in `.gitignore`). Local working collection of ~39 real recipes. Not committed and not the served folder. |

## Running and testing

The front end has nothing to build. The easiest local setup is the API's dev mode, which serves `var/www/nomnoms/` and emulates nginx's JSON listing (commands in `docs/install.md`, "Trying it locally"). A plain `python -m http.server` doesn't return a JSON listing for `recipes/`, so the app reports "Couldn't load the recipe list" unless an `index.json` exists. Validate a recipe file with `python3 -m json.tool file.json`.

Backend tests: `cd opt/nomnoms-api && npm test` (Node's built-in runner, no network or API key needed). `test/admin.test.js` and `test/photos.test.js` set `SETTINGS_FILE`/`THEME_DIR`/`USERS_FILE` (or `RECIPES_DIR`/`PHOTOS_DIR`) to a temp folder before importing, because `config.js` reads the environment once.

## How the app works (`app.js`)

- **Recipe discovery:** `loadRecipes()` fetches `recipes/` expecting nginx's `autoindex_format json` output (array of `{name, type}`), keeping `type === 'file'` entries. If that fails it falls back to `recipes/index.json` (array of file names). `index.json` is never treated as a recipe. Each file is fetched with `cache: 'no-cache'`; unreadable files are collected in `state.problems` and shown on the home page rather than failing the whole load.
- **Normalisation:** `normalizeRecipe()` turns raw JSON into a uniform shape. The slug is the file name minus `.json`. Title falls back to the slug, servings to 4, tags are lowercased, `notes` may be a string or list, steps may be strings or `{title,text,timer}`. `normalizeGroups()` flattens ingredients into groups (explicit `{group, items}` or loose entries gathered into headingless groups). A lowercase `search` string is precomputed per recipe (title, description, tags, ingredient names).
- **Routing:** hash-based. `#/r/<slug>` shows a recipe, `#/import` shows sign-in or the import screen, `#/admin` shows sign-in, the admin page, or an "admins only" notice, `#/password` shows the change-password form, and anything else shows home. While `state.user.mustChangePassword` is set, `#/import` and `#/admin` show the password form instead, and `canImport()`/`isAdmin()` are false. `route()` runs on `hashchange` and after the initial load, and always calls `leaveRecipe()` and `clearPreview()` first to clear timers, alarm, wake lock and any unsaved appearance preview. Signing in calls `route()`, so you land on the page you asked for.
- **Site identity:** `loadSite()` reads `theme/site.json` (name, favicon and the `thumbnails` switch for home-page photos) in parallel with the recipes; failures keep the defaults ("Recipes", the inline emoji icon). All tab titles go through `pageTitle()`. Fonts and corner radius are the CSS variables `--font-heading`, `--font-body` and `--radius`.
- **Rendering:** no framework. Views are built with template strings assigned to `innerHTML`; all user data goes through `esc()`. Event handling is delegated on `#app` using `data-action` attributes (`click`, `change`, `input`, `submit` and drag-and-drop listeners at the bottom; forms carry `data-action` too). New interactive elements should follow this pattern rather than attaching their own listeners. The one exception is a capture-phase `error` listener that removes `img.photo` elements whose file is missing, since load errors don't bubble.
- **State:** a single `state` object. Only the US/Metric choice persists (localStorage key `recipes:units`, via `getPref`/`setPref`, wrapped in try/catch). Servings, ticked ingredients and ticked steps reset on navigation or reload by design. `state.user` comes from `GET api/me`, loaded separately so it never delays the recipe list. `drawAccount()` then fills the home page's header slot (Import for importers and admins) and the account footer (a "Sign in" link, or "Signed in as … · Admin · Change password · Sign out", with Admin for admins only). The footer is `#account-foot` in `index.html` (left side of `.site-foot`, whose right side is a static credit with GitHub and Ko-fi links), outside `#app`, so it's on every page; `route()` redraws it, and it has its own click listener for sign-out since `#app`'s delegation can't reach it. Visitors see nothing import-related besides that footer link. `state.imp` holds the import draft until it's saved or discarded.
- **Scaling and units:** ingredient amount x (selected servings / written servings). `ALIASES`, `VOL` (ml) and `WT` (g) drive recognition and conversion in `convert()`. Metric output is rounded with `niceRound()` only when converted; US output is formatted to eighths with Unicode fractions by `fmtFraction()`. Unknown units pass through untouched and are not pluralised. `parseAmount()` accepts numbers or `"1/2"` / `"1 1/2"` strings, but not Unicode fraction characters.
- **Timers:** per-step `timer` (seconds). A 250ms `setInterval` tick updates countdowns; at zero the alarm beeps via Web Audio every 4s (plus vibrate) until dismissed. The AudioContext is created in `ensureAudio()` on the start tap, since browsers require a user gesture.
- **Wake lock:** optional "Keep screen on" checkbox using the Screen Wake Lock API, re-acquired on `visibilitychange`.
- **Admin UI:** `showAdmin()` loads `api/admin/settings` and `api/admin/users` into `state.admin` and draws three sections (`drawLook`, `drawAi`, `drawUsers`), each redrawn on its own. Colours start from a theme (radio cards; picking one fills the colour pickers via `useTheme`), with the pickers in a collapsed "Customise colours" section. `look.theme` names the base theme; it shows as customised, with a reset button, whenever the colours differ from it. `drawContrast` warns about low-contrast pairs, using the same formula and thresholds as the server. Appearance edits are read into `state.admin.look` on `input` and previewed by setting CSS variables inline on `<html>` (`previewLook`); saving reloads `theme.css` with a cache-buster. The API key field is write-only: type=password, never prefilled, cleared on submit, and copy/cut/drag are blocked on `[data-secret]` elements. Option lists and limits (themes, contrast pairs, fonts, colours, corner radius range, models, roles) come from the server, not the front end.
- **Import UI:** `api()` wraps fetch for `/api/` and always sends `X-Requested-With: nomnoms`. The flow: choose a source (file, URL or pasted text), get a draft back, review it (a preview built with `normalizeRecipe`/`amountText`, an editable JSON textarea and a file-name field), then save. A 409 response offers "replace", and on success the app reloads recipes and opens the new one. The review screen also has a Photo section (`draft.photo`, pre-filled from the page's photo on URL imports), uploaded after the recipe is saved.
- **Photos:** `normalizeRecipe` keeps `image` only if it matches `IMAGE_RE` (`photos/<name>.jpg|jpeg|png|webp`; the same regex is in `validate.js`). `drawPhoto()` fills the recipe page's hero slot and `drawPhotoTools()` the Add/Change/Remove buttons for `canImport()`; a change updates the shared recipe object and redraws only those slots, so timers survive. Every photo is decoded (`readPhoto`) and redrawn by `renderPhoto()`: scaled to `PHOTO_EDGE` (1600px) and re-encoded as JPEG on a canvas, which also drops EXIF/GPS. A chosen file goes through `editPhoto()` first, a `<dialog>` appended to `#app` with a 3:2 (`CROP_RATIO`) frame for drag, zoom (slider, wheel, pinch, keys) and crop; it resolves with the JPEG or null on cancel, and `route()` closes it. Its pointer, wheel and key handlers are delegated on `#app` like everything else (Escape's `cancel` event in the capture phase). A web page's photo uses `preparePhoto()` (whole, uncropped) until "Adjust photo" reopens the original in the editor. Hidden file inputs are opened by `data-action="pick-file"` buttons with `data-for`.

## Import service (`opt/nomnoms-api`)

Node 20+, ES modules, two dependencies (`@anthropic-ai/sdk`, `busboy`). Settings come from environment variables in `config.js`, with admin-page overrides in `settings.js`.

- `server.js`: plain `http` server with routes `GET /api/me` and `POST /api/login`, `/api/logout`, `/api/password` (any signed-in user), `/api/import` and `/api/recipes` (importer or admin), and `/api/admin/*` (admin only; listed at the top of the file). `requireRole()` gives 401 when signed out, and 403 for the wrong role or while the password is temporary. Every POST needs the `X-Requested-With: nomnoms` header (CSRF protection, alongside `SameSite=Strict` cookies). `DEV_STATIC_ROOT` also serves the site for local testing.
- `auth.js`: users file (`USERS_FILE`, re-read on each login), scrypt hashes, in-memory sessions, and per-IP/per-username login rate limiting. Client IP comes from `X-Real-IP`, trusted only from `TRUSTED_PROXIES`. Roles are `admin` and `importer` (`ROLES`); a missing role means importer and an unknown one can't sign in. `createUser`/`updateUser`/`deleteUser` are shared by the admin routes and `tools/add-user.js`, serialise writes, and refuse to remove or demote the last admin. Role changes update open sessions; password resets and removals end them (`dropSessions`). A password set for someone else (admin page, or `tools/add-user.js` without `--permanent`) gives the user `mustChangePassword: true` until they use `changePassword()`, which needs the current password and counts failures towards the login rate limit. There is deliberately no self-service "forgot password"; admins reset passwords.
- `settings.js`: admin-page settings in `SETTINGS_FILE` (0600; appearance, model/effort, API key). Every save validates against whitelists (hex colours, a known `THEMES` key, `FONTS`, a whole-pixel radius within `RADIUS`, `MODELS`, `EFFORTS`) and refuses colours where a `CONTRAST` pair is below `CONTRAST.min` (settings loaded from disk skip that check), and regenerates `THEME_DIR` files atomically; they're also rewritten at startup. `aiConfig()` merges settings over env; `keyStatus()` exposes only source and last four characters. Favicon uploads are sniffed (PNG/ICO/WebP only, 256 KB).
- `import/index.js`: sniffs input by content. Our JSON goes straight through `validate.js`. HTML or JSON with schema.org Recipe data goes through `jsonld.js` + `ingredient.js` (no LLM). PDF, images, plain text and pages without markup go to `llm.js`.
- `import/llm.js`: Claude via the SDK with structured outputs (a JSON schema) and server-side refusal fallbacks. The system prompt restates the format rules, and the schema is mapped back to the site's format. Key, model and effort come from `aiConfig()`, and the client is rebuilt when the key changes. Without a key it returns a clear 503 and the other paths still work. `testKey()` backs the admin page's Test button (lists models, free).
- `import/fetch-url.js`: SSRF-safe fetch. Only http/https on ports 80/443; every hop, including redirects, must resolve to public IPs, and the connection uses the checked address. Size and time are capped.
- `import/validate.js`: server-side mirror of `docs/recipe-format.md`. Errors block saving; warnings, such as quantities in step text, are shown for review.
- `photos.js`: `setPhoto`/`removePhoto` for `POST /api/recipes/photo` (multipart `slug` + JPEG) and `/api/recipes/photo/delete`. JPEG only, 5 MB, with APP1/APP3-15/COM segments stripped (`stripJpegMetadata`). Writes `PHOTOS_DIR/<slug>-<hash>.jpg` atomically, sets the recipe's `image`, and only ever deletes files matching its own naming. `POST /api/recipes` with `overwrite` carries the existing `image` over. URL imports also fetch the page's photo (`imageFrom`/`pageImage` in `jsonld.js`, then `fetchUrl`) and return it base64 as `photo`; a failure is only a warning.
- `save.js`: slug rules (`[a-z0-9-]`, not `index`) and an atomic write via a hidden `.tmp` file. It never overwrites unless asked.

## nginx

`nginx-nomnoms.conf` is a `default_server` on port 80 with root `/var/www/nomnoms`. `/` uses `try_files` with `Cache-Control: no-cache`. `/recipes/` enables `autoindex on; autoindex_format json;`, which is what lets new recipe files (including imported ones) appear on a page refresh without editing code or reloading nginx. Removing that block breaks recipe discovery (only the `index.json` fallback remains). Requests whose user agent matches the `$blocked_bot` map (AI crawlers and scraping libraries) get a 403 everywhere, and `/recipes/` is rate-limited per IP (`limit_req`, 2 r/s with a burst of 200 so one page load can fetch every recipe; raise the burst if the collection nears that). `/photos/` has no listing, a day's `max-age` (safe because the service's photo names change with their content) and its own `photos` rate-limit zone (2 r/s, burst 100). `/api/` proxies to the service on `127.0.0.1:3000`. HTTPS ends at a Traefik reverse proxy in front of nginx; the commented `set_real_ip_from` lines must name Traefik's address so rate limiting sees real client IPs.

## Conventions

- Front end: keep it dependency-free, with no bundler, framework or npm packages. The backend keeps its dependencies minimal and installs them with `npm ci`.
- Recipe format changes must be made in four places together: `normalizeRecipe`/related code in `app.js`, `opt/nomnoms-api/import/validate.js` (plus the LLM schema and prompt in `llm.js` if the change affects extraction), `docs/recipe-format.md`, and the example recipe (both copies).
- Recipe files: kebab-case names (`garlic-tomato-spaghetti.json`), UTF-8, strict JSON (no comments, no trailing commas). The file name is the public URL, so renaming breaks bookmarks.
- Keep quantities out of step and note text; those strings are never scaled.
- Colours live in CSS variables at the top of `style.css`, with a dark-mode override block. The same defaults are the first theme (`sea-glass`) in `THEMES` in `settings.js`; keep them in sync. A new themeable variable goes in `COLORS` and in every theme there. New themes must clear `CONTRAST.warn` for every pair in both modes (a test checks).
- Unit aliases exist in both `app.js` (`ALIASES`) and `opt/nomnoms-api/import/ingredient.js` (`UNITS`). Keep them in sync.
- Docs describe a fresh, valid install of the current layout. Don't add upgrade or migration steps (old paths, renamed files, backing up previous configs); if a change affects an existing server, say so in the commit message or to the user instead.
